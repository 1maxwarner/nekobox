# Маршрутизация в NekoBox

Этот документ описывает фактическое поведение данного форка NekoBox и
сгенерированной им конфигурации sing-box.

## Коротко: как выбирается маршрут

1. Приложение создаёт соединение через системный прокси или TUN.
2. NekoBox при необходимости добавляет служебные действия `sniff` и `resolve`.
3. sing-box проверяет правила активного профиля сверху вниз.
4. Первое совпавшее завершающее правило выбирает действие: прокси, прямое
   соединение или блокировку.
5. Если ни одно правило не совпало, используется `Default outbound` активного
   профиля.

Изменения правил применяются к новым соединениям. Уже установленные TCP- и
UDP-сеансы могут продолжать работать по старому маршруту до переподключения.

## Профили, включение и приоритет

В каждый момент используется один активный профиль маршрутизации.

- Флажок рядом с профилем определяет, можно ли его выбрать и использовать.
- Кнопка включения/выключения делает то же самое одним нажатием.
- Последний включённый профиль выключить нельзя.
- Чем меньше число приоритета, тем выше профиль находится в списке.
- Если выбранный профиль был выключен или больше не существует, NekoBox
  выбирает первый включённый профиль: сначала по меньшему приоритету, затем по
  меньшему внутреннему ID.
- Включённые профили **не объединяются**. Приоритет задаёт порядок выбора и
  резервный профиль, но не порядок правил из разных профилей.

Пример:

| Профиль | Включён | Приоритет | Результат |
| --- | --- | ---: | --- |
| Работа | да | 10 | первый резервный профиль |
| Обычный | да | 50 | доступен для ручного выбора |
| Игры | нет | 5 | не участвует, несмотря на приоритет 5 |

Если активен `Обычный`, он продолжает использоваться. Если его выключить,
автоматически будет выбран `Работа`.

## Порядок и логика совпадения правил

Правила внутри активного профиля проверяются в том порядке, в котором они
показаны в редакторе. Поэтому узкие исключения нужно помещать выше общих
правил.

В одном поле несколько значений работают как **ИЛИ**. Разные заполненные поля
одного правила работают как **И**.

Например:

```json
{
  "domain_suffix": ["youtube.com", "googlevideo.com"],
  "network": "tcp",
  "port": [443],
  "action": "route",
  "outbound": "proxy"
}
```

Правило означает:

```text
(домен оканчивается на youtube.com ИЛИ googlevideo.com)
И сеть TCP
И порт 443
```

`invert: true` инвертирует результат всего условия.

## Основные условия

| Поле редактора | Что проверяется | Пример |
| --- | --- | --- |
| `domain` | точное имя домена | `accounts.google.com` |
| `domain_suffix` | домен и его поддомены | `youtube.com` |
| `domain_keyword` | подстрока в имени | `googlevideo` |
| `domain_regex` | регулярное выражение | `(^|\.)google\..+$` |
| `ip_cidr` | адрес назначения или сеть | `1.1.1.0/24` |
| `ip_is_private` | частный адрес назначения | `true` |
| `source_ip_cidr` | исходный адрес или сеть | `192.168.1.0/24` |
| `port`, `port_range` | порт назначения | `443`, `8000:9000` |
| `network` | транспорт | `tcp` или `udp` |
| `protocol` | распознанный протокол | `dns`, `tls`, `http`, `quic` |
| `process_name` | имя процесса | `Code.exe` |
| `process_path` | полный путь процесса | `C:\Program Files\App\app.exe` |
| `process_path_regex` | путь по регулярному выражению | `(?i)\\Steam\\.*\.exe$` |
| `rule_set` | готовый набор доменов/IP | `geosite-youtube` |
| `inbound` | точка входа NekoBox | `tun-in`, `mixed-in`, `dns-in` |

Доменные правила зависят от доступности имени домена. В TUN приложение часто
соединяется уже с IP-адресом, поэтому включённый sniffing помогает восстановить
домен из TLS, HTTP или QUIC. Он не может распознать абсолютно любой
зашифрованный или нестандартный трафик.

## Действия и выходы

### `proxy`

Отправляет соединение через текущий запущенный VPN/прокси-профиль. Это обычный
вариант для заблокированных сайтов.

### `direct`

Соединяется напрямую через обычный сетевой интерфейс, минуя прокси. Подходит
для локальной сети, банковских приложений и сервисов, которым мешает VPN.

### `block`

В интерфейсе это блокировка. При сборке конфигурации NekoBox преобразует её в
действие sing-box `reject`.

### Конкретный прокси-профиль

В расширенном редакторе правило может ссылаться не только на `proxy`, но и на
конкретный сохранённый профиль. NekoBox добавит нужный outbound в итоговую
конфигурацию. Если профиль удалён, сборка конфигурации остановится с ошибкой,
чтобы трафик не ушёл неожиданным маршрутом.

### Служебные действия

- `sniff` определяет протокол и, когда это возможно, имя назначения.
- `resolve` разрешает доменное имя с выбранной стратегией IPv4/IPv6.
- `hijack-dns` передаёт DNS-запрос встроенному DNS-модулю sing-box.
- `route-options` меняет параметры маршрута без немедленного выбора outbound.
- `reject` закрывает или отбрасывает соединение.

## Простой редактор

В простом редакторе одна строка задаёт одно значение условия:

```text
domain:accounts.google.com
suffix:youtube.com
keyword:googlevideo
regex:(^|\.)google\..+$
ip:192.168.0.0/16
processName:Code.exe
processPath:C:\Program Files\App\app.exe
ruleset:geosite-youtube
```

Строки добавляются в правило выбранного действия. Для сочетаний вроде
«конкретный процесс **И** конкретный порт» нужен расширенный редактор.

## Практические примеры

### YouTube через VPN, остальное напрямую

1. Установить `Default outbound` в `direct`.
2. Создать верхнее правило:

```json
{
  "domain_suffix": ["youtube.com", "googlevideo.com", "ytimg.com"],
  "action": "route",
  "outbound": "proxy"
}
```

Если часть видео идёт напрямую, включить sniffing и добавить соответствующий
rule-set: CDN часто использует много доменов.

### VS Code напрямую

```json
{
  "process_name": ["Code.exe"],
  "action": "route",
  "outbound": "direct"
}
```

Это правило нужно разместить выше общего правила «всё через proxy».

### Заблокировать телеметрию Microsoft

```json
{
  "domain": ["watson.events.data.microsoft.com"],
  "action": "reject"
}
```

Для группы доменов практичнее использовать `domain_suffix` или отдельный
rule-set.

### Локальная сеть всегда напрямую

```json
{
  "ip_is_private": true,
  "action": "route",
  "outbound": "direct"
}
```

Если нужно ограничить правило только своей сетью:

```json
{
  "ip_cidr": ["192.168.1.0/24"],
  "action": "route",
  "outbound": "direct"
}
```

### Только HTTPS выбранного домена через VPN

```json
{
  "domain_suffix": ["example.com"],
  "network": "tcp",
  "port": [443],
  "action": "route",
  "outbound": "proxy"
}
```

## Rule-set

Rule-set — внешний или встроенный список правил. Он удобнее сотен отдельных
доменов и сетей. NekoBox принимает известное имя rule-set либо прямой URL на
`.srs` или `.json`, создаёт уникальный tag и добавляет его в `route.rule_set`.

Пример:

```json
{
  "rule_set": ["geosite-youtube"],
  "action": "route",
  "outbound": "proxy"
}
```

Удалённый rule-set должен быть доступен при запуске/обновлении. Ошибка загрузки
набора способна сделать зависящее от него правило неработоспособным.

## DNS и маршрутизация

В стандартном режиме NekoBox создаёт несколько DNS-серверов:

- `dns-remote` — удалённый DNS, запросы к которому идут через текущий proxy;
- `dns-direct` — прямой DNS;
- `dns-local` — базовый системный или заданный вручную резолвер, необходимый в
  том числе для разрешения адреса самого DNS-сервера без рекурсии;
- `dns-fake` — добавляется при включённом FakeIP.

Домены из правил `direct` автоматически используются для прямого DNS, чтобы
получить адрес, подходящий для прямого соединения. Поле выбора конечного DNS
определяет, будет ли запрос без специального DNS-правила отправлен в
`dns-remote` или `dns-direct`.

`hijack-dns` перехватывает DNS из TUN и передаёт его встроенному модулю. Это
предотвращает обход правил приложениями, которые обращаются к обычному DNS на
порту 53, но не перехватывает любой произвольный DoH внутри приложения.

Сообщение вида:

```text
dns: exchange failed ... stream ... canceled by remote
```

означает сбой транспорта между NekoBox и удалённым DNS через прокси. Это не
доказательство ошибки совпадения доменного правила: удалённая сторона или
промежуточный HTTP/2/HTTP/3-транспорт отменил поток.

## TUN и правила по процессам

В VPN/TUN-режиме NekoBox дополнительно добавляет служебные правила перехвата
DNS, `resolve` и `sniff`. Списки процессов `proxy`, `direct` и `block` из
настроек TUN добавляются **после** правил активного профиля.

Следствие: более раннее правило профиля может сработать раньше правила TUN по
процессу. Если маршрутизация приложения критична, поместите правило
`process_name`/`process_path` в начало самого профиля.

Опция исключения прямых CIDR/rule-set на уровне TUN также может добавить сети в
маршруты Windows. Большие наборы адресов способны заметно нагрузить Windows,
поэтому эту функцию следует включать только при необходимости.

## Частые ошибки

- Общее правило стоит выше исключения и перехватывает его трафик.
- В `domain` указан суффикс. Для всех поддоменов обычно нужен
  `domain_suffix`.
- Доменные правила не срабатывают в TUN, потому что sniffing выключен и
  приложение подключается непосредственно к IP.
- Правило процесса использует отображаемое название приложения вместо имени
  исполняемого файла, например нужно `Code.exe`.
- Удалён rule-set или конкретный outbound, на который ссылается профиль.
- Пользователь ожидает, что несколько включённых профилей сложатся вместе.
  В этой версии активен только один профиль.
- После изменения проверяется старое уже открытое соединение. Для чистого
  теста перезапустите приложение-клиент или его соединение.

## Рекомендуемый базовый профиль

Для схемы «почти всё через VPN, локальное и доверенное напрямую»:

1. Правила конкретных процессов `direct`.
2. Частные сети и локальные адреса `direct`.
3. Точечные блокировки `reject`.
4. Специальные доменные и rule-set правила.
5. `Default outbound = proxy`.

Для схемы «VPN только для выбранных сайтов»:

1. Домены и rule-set нужных сайтов через `proxy`.
2. При необходимости отдельные блокировки.
3. `Default outbound = direct`.
